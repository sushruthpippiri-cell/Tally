1. Introduction
1.1 Purpose

This document specifies a web-based platform that:

  1. Extracts accounting, inventory and transaction data from TallyPrime into a PostgreSQL database, using custom TDL
     (Tally Definition Language) Collections and Reports invoked over Tally’s XML/HTTP interface, through a local Tally
     Sync Agent.
  2. Presents a business analytics dashboard computed only by direct, deterministic aggregation of the synced data. No AI,
     ML or LLM component is used in the analytics.
  3. Verifies that the local data matches Tally through an independent reconciliation process.
  4. Optionally offers anomaly detection, where anomalies are found by deterministic rules and an LLM (Claude, via an MCP
     server) may be used only to write a plain-language explanation of evidence the application has already computed.

1.2 Scope

In scope

       TDL-driven, one-way synchronization (Tally → platform) of companies, groups, ledgers, voucher types, stock items, cost
       centres, opening balances, stock snapshots, and vouchers (header, ledger entries, inventory entries, bill allocations, cost-
       centre allocations).
       Local Tally Sync Agent (Windows), supporting one or more Agents per company.
       AI-free analytics: sales, purchases, customer and product revenue, expenses, cash flow, balances, receivables/payables
       aging, customer payment behaviour, stock movement.
       Reconciliation of local data against Tally totals.
       Drill-down from every summary figure to the vouchers behind it; CSV/PDF export.
       Authentication, role-based access control, company (tenant) isolation, audit logging.
       Optional, feature-flagged anomaly detection with optional AI explanation.
       Responsive web interface usable on phone-width screens.

Out of scope

       Writing any data back into Tally (no two-way sync, no data entry, no invoice creation).
       Payroll.
       Forecasting and natural-language querying.
       Replacing Tally as the system of record for statutory compliance.
       GST analytics (default; see OPEN — BUSINESS DECISION in Section 8.15).
       Multi-company consolidated reporting in the user interface (the data model supports multiple companies; the v1 interface
       works with one company at a time).

2. Overall Description
2.1 Product perspective

The platform sits beside Tally and never replaces it. Tally remains the source of truth for the books. The platform keeps a
synchronized, read-only copy for analysis, and proves through reconciliation that the copy matches.

The system has two layers:

     Core layer (always on, no AI): Agent, synchronization, database, analytics, reconciliation, dashboard. It works fully with
     no AI service.
     Optional anomaly layer (off by default): deterministic anomaly rules, plus an optional Claude explanation through
     MCP. Turning it off, or losing the AI service, never affects the core layer.

2.2 User classes

                    User class                                      Description                                       Key needs

 Owner                                             Business owner, usually non-technical            Clear dashboard, trustworthy numbers, control
                                                                                                    of users and connections

 Accountant                                        Manages the books in Tally                       Accurate figures, sync status, reconciliation,
                                                                                                    anomaly review

 Admin/Developer                                   Maintains the integration                        Agent management, TDL definitions, logs,
                                                                                                    configuration


2.3 Operating environment

                                 Component                                                              Environment

 TallyPrime                                                                Windows machine, XML/HTTP server enabled, custom TDL files loaded,
                                                                           running in a logged-in user session

 Tally Sync Agent                                                          Windows service on the Tally machine or a machine on the same LAN
                                                                           that can reach Tally’s port

 Backend                                                                   Python (FastAPI), containerized (Docker), cloud-hosted

 Database                                                                  PostgreSQL (production). SQLite is permitted only for isolated local unit
                                                                           tests

 Frontend                                                                  React single-page application in a modern browser, desktop or phone

 Optional                                                                  MCP server (Python mcp SDK) and Claude, used only when anomaly
                                                                           detection is enabled


2.4 Design constraints

  1. The analytics layer must not call any AI, ML or LLM component. Every figure must be traceable to a deterministic query
     over synced data.
  2. Data extraction uses custom TDL Collections/Reports, not Tally’s default reports, so the fields returned are controlled.
  3. The Agent initiates every connection. The backend never connects into a customer network.
  4. No synced accounting record is ever hard-deleted.
  5. No MCP tool may execute arbitrary SQL, write to the database, or write to Tally.
  6. Tally provides no push notifications; all synchronization is pull-based.

2.5 Assumptions and dependencies

  1. The company’s chart of accounts is set up in Tally before synchronization.
  2. Bill-wise details are maintained in Tally for ledgers where bill-wise aging is expected. Ledgers without them are reported
     without aging buckets (Section 10.3).
  3. Custom TDL files are loaded into Tally on each Agent machine.
  4. TallyPrime is kept running in a logged-in Windows session while synchronization is expected.
  5. If anomaly explanation is enabled, Claude is reachable through the MCP client.
3. Architecture and Deployment
3.1 Deployment topology

A cloud-hosted backend cannot open a connection to a private address such as 192.168.x.x inside a customer’s network. The
platform therefore uses a local Agent that makes outbound HTTPS calls only. No firewall change, port forwarding or VPN is
needed on the customer side.

 Browser ──► React Frontend ──► FastAPI Backend ──► PostgreSQL
                                      ▲
                                      │ outbound HTTPS only
                                      │ (heartbeat, command polling,
                                      │ sync batch upload)
               ┌──────────────────────┼──────────────────────┐
               │                      │                      │
         Agent A                Agent B               Agent C
         (head office)          (branch)              (standby / manual failover)
               │ local XML/HTTP        │                      │
               ▼                      ▼                      ▼
         TallyPrime + TDL       TallyPrime + TDL       TallyPrime + TDL
         (company X)            (company X)            (company X)

3.3 Direct-connect mode

If the backend runs on infrastructure the business controls on the same network as Tally, the Agent software runs on that
backend host and reaches Tally directly. The data model, identity rules and synchronization logic are identical in both modes;
only where the Agent runs changes.



4. Tally Sync Agent
4.1 Responsibilities

The Agent (1) registers once with the backend, (2) sends heartbeats and polls for commands, (3) pulls data from Tally using the
TDL Collections, (4) uploads data in batches, (5) buffers data locally when the backend is unreachable, and (6) reports Tally and
Agent status.

4.2 Registration and onboarding

                                             Step                                                                    Action

 1                                                                                  Owner creates a company account in the web application

 2                                                                                  Backend creates a companies row (inactive until an Agent is
                                                                                    confirmed)

 3                                                                                  Owner/Admin generates a one-time registration token (valid 24
                                                                                    hours) for that company

 4                                                                                  The customer installs the Agent on the Tally machine and gives it a
                                                                                    name (e.g. “Head Office”)

 5                                                                                  The customer enters the registration token in the Agent

 6                                                                                  The Agent reads the Tally company’s name and GUID from local Tally
                                                                                    and sends them with the token

 7                                                                                  Backend validates the token, creates an agents row bound to the
                                                                                    company, stores the Tally GUID and company name, and returns a
                                                                                    permanent Agent credential
 8                                                              Backend marks the company active (if this is its first Agent) and
                                                                returns configuration: poll interval, batch size, TDL definitions expected

 9                                                              The Agent begins heartbeats

 10                                                             Owner/Admin triggers the initial full sync


For a company’s first Agent, the Tally GUID it reports becomes the company’s tally_guid. Every later Agent for the same
company must report the same GUID, or registration is rejected with COMPANY_MISMATCH.

4.3 Agent authentication

                              ID                                                             Requirement

 SEC-2.0                                                        All Agent–backend traffic uses HTTPS with TLS 1.2 or later

 SEC-2.0a                                                       Each Agent holds its own long random credential, sent as a bearer
                                                                token on every request

 SEC-2.0b                                                       The backend stores only a salted hash of each credential and verifies
                                                                requests by hashing and comparing

 SEC-2.4                                                        No HMAC request-signing scheme is used or claimed. The model is
                                                                bearer credential over TLS only


4.4 Credential rotation and revocation

                             Step                                                               Rotation

 1                                                              Owner/Admin requests rotation for one Agent from the dashboard

 2                                                              Backend generates a new credential and invalidates the old hash in the
                                                                same transaction

 3                                                              The new credential is shown once to the requesting user in their
                                                                authenticated session. It is never pushed to the Agent

 4                                                              The user enters the new credential into the Agent’s configuration

 5                                                              Calls with the old credential are rejected with 401
                                                                CREDENTIAL_INVALID


                              ID                                                             Requirement

 SEC-2.1                                                        Rotation invalidates the old credential atomically with issuing the new
                                                                one. There is no window where both are valid

 SEC-2.2                                                        An invalid or revoked credential is rejected with a distinguishable error
                                                                (CREDENTIAL_INVALID or AGENT_REVOKED)

 SEC-2.3                                                        Rotation keeps the same agent_id. Revocation is permanent; the
                                                                installation must re-register as a new Agent


4.5 Multiple Agents per company

One company can have one or more Agents (branch installations, separate Tally environments, a standby Agent). One Agent
serves exactly one Tally company.

                         Agent state                                                            Meaning

 REGISTERING                                                    Token exchanged; awaiting first successful Tally GUID confirmation

 ACTIVE                                                         Heartbeating normally

 OFFLINE                                                        No heartbeat within the offline threshold (default 5 minutes,
                                                                IMPLEMENTATION TEST)

 INCOMPATIBLE                                                   Heartbeating, but its version or TDL version is below the backend
                                                                minimum

 REVOKED                                                        Credential revoked; permanently rejected


Standby Agents: there is no automatic failover. If a primary Agent is offline or its command fails, an Owner/Admin sends a
new command to the standby Agent. Automatic failover is a possible future feature, not part of this specification.

4.8 Heartbeat, command polling and recovery

The backend never contacts an Agent. Manual and scheduled syncs reach the Agent as commands it collects when it polls.

 Agent ── heartbeat/poll every 30 s ──────────► Backend
 Agent ◄─ pending command for this agent_id ── Backend
 Agent ── claim (PENDING → CLAIMED) ──────────► Backend
 Agent ── RUNNING + progress heartbeats         Backend
 Agent ── TDL export ──► TallyPrime
 Agent ── sync batches ───────────────────────► Backend
 Agent ── COMPLETED / FAILED ─────────────────► Backend




                                               ID                                            Requirement

 AGT-1.1                                                       The Agent polls at a configurable interval, default 30 seconds. The
                                                               heartbeat carries Agent version, TDL version, Tally version where
                                                               available, Tally process uptime and queue status

 AGT-1.2                                                       Command states: PENDING → CLAIMED → RUNNING → COMPLETED, or
                                                               FAILED, EXPIRED, FAILED_AGENT_LOST

 AGT-1.3                                                       Claiming is an atomic compare-and-set on the command’s status, so a
                                                               command can be claimed only once

 AGT-1.4                                                       A failed command is not retried automatically; a new command must
                                                               be issued

 AGT-1.5                                                       “Sync Now” creates a PENDING command; it never attempts to connect
                                                               to the Agent

 AGT-1.6                                                       Command status is visible on the dashboard as it changes

 AGT-1.7                                                       A RUNNING command has a lease deadline (lease_expires_at) that
                                                               the Agent extends with progress heartbeats

 AGT-1.8                                                       If the lease deadline passes, the command becomes
                                                               FAILED_AGENT_LOST and the reason is recorded

 AGT-1.9                                                       A FAILED_AGENT_LOST or EXPIRED command is never reassigned to
                                                               another Agent

 AGT-1.10                                                      A PENDING command not claimed within a configurable window (default
                                                               10 minutes) becomes EXPIRED

5. Data Model
5.1 Principles

 1. Every company-scoped table carries company_id, even though the v1 interface works with one company at a time. Adding
    a company is a new row, not a schema change.
 2. Every synced master and voucher is identified by (company_id, tally_guid). Voucher numbers are for display only.
 3. Every synced master and voucher stores its latest alter_id and a lifecycle status.
 4. Accounting amounts are stored in a normalized form that does not depend on Tally’s raw XML sign format.
 5. No synced accounting record is hard-deleted.

6. Synchronization
6.1 Sync modes

                        Mode                                  Behaviour

Initial full sync               Pulls every record of every collection with no ALTERID filter and sets
                                the watermarks

Incremental sync                Pulls records with ALTERID greater than the collection’s watermark.
                                Default schedule hourly

Manual sync                     “Sync Now” creates a command (Section 4.8); runs incremental by
                                default

Date-range sync                 Manual, for re-verifying a period. Does not move a watermark unless it
                                processes records beyond it

Reconciliation sync             Daily by default: pulls totals and key lists and compares them with
                                local data (Section 9)


6.2 Watermarks

                           ID                                Requirement

SYNC-1.1                        Each (company_id, collection_type) has its own watermark.
                                Collections are synced as independent streams

SYNC-1.2                        A watermark advances only after the batch containing those records
                                has been committed

SYNC-1.3                        The shared per-company watermark is valid only while all of a
                                company’s Agents connect to the same Tally company GUID.
                                Consolidating separate Tally companies under one business account is
                                outside this specification


6.3 Sync lease

                           ID                                Requirement

SYNC-4.1                        Before syncing a collection, an Agent acquires the lease on its
                                sync_watermarks row with an atomic compare-and-set

SYNC-4.2                        If another Agent holds an unexpired lease, the request is rejected with
                                SYNC_LOCKED and nothing is pulled for that collection

SYNC-4.3                        The lease is released on completion, or reclaimed automatically after
                                lock_expires_at

SYNC-4.4                        The lease prevents concurrent writers; stale-record protection (Section
                                6.4) prevents out-of-order data. Both are required
6.4 Stale-record protection

                              ID                                                                  Requirement

 SYNC-3.1                                                           Every upsert compares the incoming ALTERID with the stored ALTERID
                                                                    for that (company_id, GUID)

 SYNC-3.2                                                           Incoming lower than stored: the record is rejected, the local record is
                                                                    unchanged, and STALE_ALTERID is logged

 SYNC-3.3                                                           Equal: no change, not an error

 SYNC-3.4                                                           Higher: the update is applied (Section 6.9 for vouchers)

 SYNC-3.5                                                           This rule applies to groups, ledgers, voucher types, stock items, cost
                                                                    centres and vouchers


6.5 Batching, idempotency and partial failure

                              ID                                                                  Requirement

 SYNC-6.1                                                           The backend commits uploads in batches (default 500 records), each in
                                                                    its own transaction

 SYNC-6.2                                                           Each voucher’s full write (header, entries, bill allocations, cost-centre
                                                                    allocations, items) is one transaction; a voucher is never left partly
                                                                    written

 SYNC-6.3                                                           Every write is an upsert keyed on (company_id, tally_guid), so
                                                                    replaying a batch is always safe

 SYNC-6.4                                                           If a run fails part-way (for example after 50,000 of 100,000 records),
                                                                    committed batches remain, the watermark reflects the last committed
                                                                    batch, the run is marked PARTIAL, and the next run resumes from the
                                                                    watermark with no duplicates

 SYNC-6.5                                                           A record that cannot be parsed is logged to sync_errors; the rest of
                                                                    the batch continues

 SYNC-6.6                                                           If Tally is unreachable, no local data is changed

8. Accounting and Analytics Rules
8.1 Core principles
  1. Every metric is computed by direct SQL/pandas aggregation over synced data. No AI, ML or LLM component is used.
  2. Every metric filters ledger entries by both the ledger’s primary group and the entry’s accounting direction. A voucher’s
     entries are never summed as a whole, because a balanced voucher’s debits and credits cancel out.
  3. Standard analytics include only ACTIVE vouchers. CANCELLED and MISSING_IN_TALLY vouchers are excluded unless the
     user explicitly asks to see them.
  4. All date grouping uses company_timezone (Section 17.5).

8.2 Ledger classification by primary group

                              ID                                                               Requirement

 ACC-7.1                                                           Every rule that classifies a ledger (sales, purchase, expense, cash,
                                                                   bank, duties and taxes, customer, supplier) uses the ledger’s primary
                                                                   group, never its immediate parent

 ACC-7.2                                                           The primary group is resolved at sync time by following parent groups
                                                                   to a predefined primary group, and cached

 ACC-7.3                                                           Classification allow-lists in company_settings contain primary groups
                                                                   only

 ACC-7.4                                                           A group whose chain does not reach a primary group (missing parent
                                                                   or a loop) is marked UNRESOLVED_GROUP; its ledgers are excluded from
                                                                   classified metrics and listed for data-quality review

 ACC-7.5                                                           When a group’s parent changes, primary groups are recalculated for it
                                                                   and everything beneath it on the next sync, and the change is logged

 ACC-7.6                                                           Customers are ledgers whose primary group is Sundry Debtors;
                                                                   suppliers are ledgers whose primary group is Sundry Creditors


Default allow-lists: Sales = Sales Accounts; Purchase = Purchase Accounts; Expense = Direct Expenses, Indirect Expenses;
Cash/Bank = Cash-in-Hand, Bank Accounts; Tax = Duties & Taxes.

9. Reconciliation
9.1 Purpose

Reconciliation answers “does the local database match Tally?” using totals from a separate TDL Totals Collection, not by re-
adding the synced detail rows. This way a bug in the sync or parser cannot hide itself.

9.2 Tolerance rule

 absolute_difference   = |tally_value − local_value|
 percentage_difference = absolute_difference / |tally_value| × 100        (tally_value ≠ 0)

 If tally_value = 0:   PASS when local_value = 0, otherwise FAIL.
 Otherwise:            PASS when absolute_difference ≤ absolute tolerance
                            OR percentage_difference ≤ percentage tolerance.
                       FAIL only when both tolerances are exceeded.

12.2 Flow

         → MCP server tool get_anomaly_evidence(anomaly_id) → MCP client → Claude

The application’s rules engine finds every anomaly and computes every number. Claude only reads the evidence for one
anomaly and writes an explanation of it.

12.3 Rules

                                               ID                                                                             Requirement

 FR-3.1                                                                                         Nothing in this section runs while the feature flag is off

 FR-3.2                                                                                         Unusually large transaction: for each party ledger, compute the
                                                                                                mean and standard deviation of transaction amounts over a trailing
                                                                                                window (default 180 days). Flag a transaction above mean + 3
                                                                                                standard deviations, or above the previous maximum × a configurable
                                                                                                multiplier (default not set; rule inactive until configured,
                                                                                                IMPLEMENTATION TEST)

 FR-3.3                                                                                         Possible duplicate: same party ledger, same amount, within a
                                                                                                configurable window (default 3 days)

 FR-3.4                                                                                         Every flag stores the transaction amount, historical average, historical
                                                                                                maximum, deviation percentage and the rule triggered

 FR-3.5                                                                                         The MCP tool returns only the stored evidence for one anomaly; it
                                                                                                never returns bulk data and never runs arbitrary queries

 FR-3.6                                                                                         Claude is asked only to explain the supplied evidence; it is never asked
                                                                                                to calculate a number

 FR-3.7                                                                                         Evidence and explanation are shown in separate, clearly labelled areas

 FR-3.8                                                                                         A user can mark a flag “reviewed” or “not an issue”; this is recorded in
                                                                                                audit_logs

 FR-3.9                                                                                         Every MCP tool call is recorded in ai_tool_log

Example evidence: transaction ₹4,50,000; historical average ₹70,000; previous maximum ₹1,20,000; deviation +543%; rule:
amount above mean + 3 SD.

12.4 Why Claude, and does the system need it?

Claude turns numeric evidence into a sentence a non-technical owner can act on. It is not needed for detection or for any
figure. With the flag on and Claude unavailable, anomalies are still found and shown with their evidence. With the flag off, the
core system is unaffected.

20. Use Cases
UC-1 Onboarding. Owner creates the company, generates a registration token, installs and names the Agent, enters the
token; the Agent confirms the Tally company; the Owner triggers the initial full sync.

UC-2 Scheduled incremental sync. A schedule creates a command for its Agent; the Agent claims it, acquires the leases,
pulls changes above each watermark, runs the key-list check, uploads batches, and completes; the dashboard updates.

UC-3 Manual sync with several Agents. The Owner clicks “Sync Now”, chooses an Agent, and only that Agent claims the
command.

UC-4 Modified voucher. A voucher edited in Tally is pulled with a higher ALTERID; its children are replaced in one transaction
and the change is audited.

UC-5 Cancelled and deleted vouchers. A cancelled voucher becomes CANCELLED; a deleted voucher becomes
MISSING_IN_TALLY after the key-list check; neither row is deleted.

UC-6 Stale record. A retried older batch arrives after a newer one; the older record is rejected and logged.

UC-7 Concurrent Agents. Two Agents try to sync the same collection; one gets the lease, the other receives SYNC_LOCKED.
UC-8 Agent crash. An Agent crashes mid-sync; the command becomes FAILED_AGENT_LOST; the Owner issues a new
command.

UC-9 Credential rotation. The Owner rotates an Agent’s credential, sees the new value once, and enters it in the Agent.

UC-10 Reconciliation review. The Accountant opens Reconciliation, sees Tally and local values with differences, and
investigates any FAIL.

UC-11 Analytics review and export. The Owner reviews sales, cash position and aging for a period, drills into a customer’s
vouchers, and exports the view.

UC-12 Product Attribution Difference review. The Accountant drills into the difference to see which vouchers contain
revenue not tied to stock items.

UC-13 Anomaly review (optional). A large transaction is flagged with evidence and, if available, an explanation; the
Accountant marks it reviewed.

UC-14 Data-quality review. The Admin checks unresolved groups, unresolved voucher types, missing opening balances and
unlinked notes.

24. Acceptance Criteria
Each criterion is written as Given / When / Then and is the basis of a test case with the same ID.

24.1 Synchronization and identity

AC-01 Full sync. Given Tally holds X active vouchers, when a full sync runs, then the database holds exactly X corresponding
vouchers keyed by (company_id, GUID), and running it again adds no rows.

AC-02 Modified voucher. Given voucher 100 was synced at ₹10,000, when it is edited in Tally to ₹15,000 and an incremental
sync runs, then the local voucher shows ₹15,000 and audit_logs records the old and new values.

AC-03 Cancelled voucher. Given a synced voucher is cancelled in Tally, when an incremental sync runs, then its status is
CANCELLED, the row still exists, and it is excluded from standard analytics.

AC-04 Deleted voucher. Given a synced voucher is deleted in Tally, when the next incremental sync and key-list check
complete, then its status is MISSING_IN_TALLY, the row still exists, and it appears in the Data Quality view.

AC-05 Partial failure. Given a sync fails after 50,000 of 100,000 records, when the next sync runs, then it resumes from the
last committed watermark, no duplicates exist, and the failed run is recorded as PARTIAL.

AC-06 Stale record. Given a local voucher with ALTERID 108, when a record for it with ALTERID 106 arrives, then the local
voucher is unchanged and STALE_ALTERID is logged.

AC-07 Independent watermarks. Given the Voucher watermark is 500 and the Ledger watermark is 50, when an
incremental sync runs, then each collection is pulled from its own watermark and a ledger change is neither skipped nor
affected by the voucher watermark.

AC-08 Child replacement. Given a synced voucher is modified and no stable line identifier exists, when it is synced, then all
its child rows are replaced in one transaction and no orphaned or duplicate child rows remain.

AC-09 Sync lease. Given two Agents request the same company and collection at the same time, when both try to acquire the
lease, then exactly one succeeds and the other receives SYNC_LOCKED without pulling data.

AC-10 Master disappears. Given a synced ledger is missing from a full reconciliation, when reconciliation completes, then the
ledger is MISSING_IN_TALLY, is not deleted, and historical vouchers still reference it.

AC-11 Master reappears. Given a MISSING_IN_TALLY ledger appears again with the same GUID, when it is synced, then it
becomes ACTIVE and the event is audited.

AC-12 Failed ALTERID gate. Given a validation-gate row for a collection is FAILED, when syncs run, then that collection is
synced by full pull only and the dashboard shows “Full sync only”.
24.2 Agent

AC-13 Registration. Given a valid registration token, when the Agent registers, then an Agent credential is issued and bound
to exactly one company.

AC-14 Second Agent, different company. Given a company already bound to Tally GUID G1, when a new Agent registers
reporting GUID G2, then registration is rejected with COMPANY_MISMATCH.

AC-15 Revocation. Given an Agent is revoked, when it next sends a heartbeat, then it receives AGENT_REVOKED and no
commands.

AC-16 Rotation. Given an Agent’s credential is rotated, when the Agent uses the old credential, then it receives 401
CREDENTIAL_INVALID, and the new credential works.

AC-17 Manual sync by polling. Given the Owner clicks “Sync Now”, when the Agent next polls, then it claims the command,
which moves through CLAIMED, RUNNING and COMPLETED, each shown on the dashboard.

AC-18 Routing. Given two active Agents, when a sync request has no agent_id, then it is rejected; when it names one Agent,
then only that Agent receives the command.

AC-19 Offline Agent. Given the chosen Agent is offline, when a command is created for it, then it stays PENDING with “Agent
offline” shown, and is claimed when the Agent returns unless it expires.

AC-20 Agent crash. Given a command is RUNNING and the Agent stops heartbeating past the lease deadline, then the
command becomes FAILED_AGENT_LOST and is not reassigned.

AC-21 Queue full. Given the Agent’s queue reaches its limit, then the Agent stops pulling new data, keeps retrying uploads
and reports QUEUE_FULL.

AC-22 Version check. Given an Agent below the minimum version, when it sends a heartbeat, then it is marked
INCOMPATIBLE and receives no commands.

AC-23 Company targeting. Given two companies are loaded in Tally and the other one is active, when the Agent syncs, then
it pulls only from its registered company; if that company is closed, it reports COMPANY_NOT_LOADED and pulls nothing.

AC-24 Batch limit. Given a configured batch size of 15,000, then the setting is rejected; given a Tally request exceeds the
timeout, then it is retried once at half size and logged as TALLY_EXPORT_TIMEOUT.

AC-25 Uptime advisory. Given Tally’s uptime exceeds the threshold, then a restart advisory is shown against that Agent.

24.3 Accounting and analytics

AC-26 Sales is single-sided. Given a Sales voucher debiting a customer ₹10,000 and crediting Sales ₹10,000, when Total
Sales Revenue is computed, then it is ₹10,000 — not ₹20,000 and not ₹0.

AC-27 Purchases. Given a Purchase voucher with matching debit and credit entries, then Purchase Value counts only the
debit on the purchase ledger.

AC-28 Nested groups. Given a ledger under “Sales – Online”, itself under Sales Accounts, then its qualifying credits are
included in Total Sales Revenue.

AC-29 Custom voucher type. Given a “POS Invoice” voucher type derived from Sales, then its vouchers are included in sales
exactly like Sales vouchers.

AC-30 Customer attribution. Given a Sales voucher with exactly one customer ledger and ₹50,000 revenue, then ₹50,000 is
attributed to that customer.

AC-31 Cash sale. Given a Sales voucher with no customer ledger, then its revenue is Unattributed Customer Revenue, and
customer-attributed plus unattributed revenue equals Total Sales Revenue.

AC-32 Product Attribution Difference. Given a Sales voucher with ₹92,000 of stock-item lines and an ₹8,000 service line,
and gate G28 not yet passed, then Total Sales Revenue is ₹100,000, Product-attributed Revenue ₹92,000, and ₹8,000 is shown
as Product Attribution Difference, not as service revenue.

AC-33 Top-N. Given N = 10 and 25 customers with sales, then the Top view shows 10, does not claim their sum equals total
sales, and “View All” shows 25.

AC-34 Sign normalization. Given raw Tally entries, when parsed, then accounting_direction, is_debit and
amount_absolute are correct, and no analytics query reads amount_raw.

AC-35 Linked return. Given a Credit Note linked by bill reference to a Sales invoice, then it reduces Total Sales Revenue.

AC-36 Unlinked note. Given a Credit Note with no bill link, then it is UNLINKED_CREDIT_NOTE, is not subtracted, and appears in
Unclassified Adjustments.

AC-37 Cash flow. Given a Receipt of ₹5,000, a Payment of ₹3,000 and a Contra transfer of ₹10,000, then the net cash flow
shows +₹5,000 and −₹3,000, and the Contra is excluded.

AC-38 Ledger balance. Given a bank ledger with a ₹50,000 debit opening balance and ₹20,000 net debit movements up to
date D, then its balance on D is ₹70,000 debit and matches Tally within tolerance.

AC-39 Screen and export match. Given the same filters, then dashboard, drill-down total and CSV/PDF export show identical
figures.
24.4 Reconciliation

AC-40 Display. Given Tally total X and local total Y, then reconciliation shows X, Y, the absolute and percentage difference,
and PASS or FAIL.

AC-41 Both tolerances exceeded. Given Tally ₹100,000 and local ₹100,012 with tolerances ₹1 and 0.01%, then the result is
FAIL.

AC-42 One tolerance met. Given Tally ₹100,000 and local ₹100,010, then the result is PASS.

AC-43 Zero Tally value. Given a Tally value of 0, then a local value of 0 passes and a local value of 50 fails.

AC-44 Quantity tolerance. Given Tally stock of 100 units and local 98 with tolerances 0 units and 0.5%, then the result is
FAIL.

24.5 Aging, payment behaviour and stock

AC-45 Overdue bucket. Given a bill with ₹20,000 outstanding and a due date 45 days ago, then it appears in 31–60 days with
₹20,000.

AC-46 Not yet due. Given a bill due in 5 days, then it is “Not yet due”, never overdue and never negative.

AC-47 No due date. Given a bill without a due date, then it is “Due date unavailable”.

AC-48 Advance. Given a customer receipt allocated as Advance, then it appears under customer “Unadjusted Advances” and
in no aging bucket.

AC-49 On Account. Given a payment allocated On Account, then it appears under “On-Account / Unallocated” and in no aging
bucket.

AC-50 Receivable and payable separation. Given a customer advance and a supplier advance of the same amount, then
they appear on their respective sides and are not netted.

AC-51 Payment behaviour. Given a ₹10,000 bill dated 1 June, settled ₹6,000 on 11 June and ₹4,000 on 21 June, then
average days to pay is 14.

AC-52 Never sold. Given an item with stock above zero and no sales history, then it is Never Sold, not Slow-moving or Dead.

AC-53 Dead stock from snapshot. Given an item with a snapshot quantity of 40 and no sale for 200 days, then it is Dead
stock and the snapshot date is shown.

AC-54 Unit limitation. Given unit data is unavailable and an item sold in two units, then the item is flagged and the stock
view states the limitation.

24.6 Anomaly detection

AC-55 Flag off. Given anomaly detection is off, when syncs complete, then no anomaly records are created and no MCP or
Claude calls are made.

AC-56 Large transaction. Given a transaction above mean + 3 standard deviations for its party, then an anomaly record is
created with amount, average, maximum, deviation and rule.

AC-57 Duplicate. Given two vouchers for the same party and amount within 3 days, then a duplicate anomaly is created
referencing both.

AC-58 Claude unavailable. Given anomaly detection is on and Claude is unreachable, then anomalies are still created and
shown with evidence, and the explanation is marked unavailable.

AC-59 RBAC. Given an Accountant, when they call a Settings or user-management endpoint, then the API returns 403

AC-60 Tenant isolation. Given a user of company A, when they request any company B resource, then they receive 403 and
no data.

AC-61 Custom field. Given a mapped custom voucher field, when a voucher with it is synced, then the value appears in drill-

AC-62 Time zone. Given company_timezone Asia/Kolkata and a transaction at 11:58 PM IST on day 1, then daily grouping
places it on day 1 regardless of server time zone.

AC-63 Financial quarter. Given a 1 April financial year start, then an August transaction falls in Q2.

AC-64 Performance. Given the Section 17.2 environment and dataset, when the performance suite runs, then the Section
17.1 targets are met and every PERF-VAL-1 field is recorded.

AC-65 Responsive layout. Given a 360 px viewport, then no view scrolls horizontally at page level and filters and drill-downs
work by touch.

AC-66 Contract test. Given the malformed-XML fixture, when parsed, then an error is logged and no unhandled exception
occurs.

26. Technical Reviewer Questions
Architecture and connectivity

 1. How does a cloud website reach Tally on a customer’s LAN? It doesn’t. A local Agent makes outbound HTTPS calls to the
    backend, so nothing needs to reach into the customer network.
 2. Why not open a firewall port to Tally? It depends on customer network setup and would expose an unauthenticated XML
    server to the internet.
 3. How does an outbound-only Agent receive “Sync Now”? It polls every 30 seconds and collects any pending command
    addressed to it.
 4. Can one company have several Agents? Yes, one per Tally installation. Each Agent serves exactly one Tally company.
 5. How is the Agent for “Sync Now” chosen? Automatically if there is one active Agent; otherwise the user must choose.
 6. What happens if the Agent is offline? The command waits as PENDING with a visible status, and is collected when the Agent
    returns or expires.
 7. Does a standby Agent take over automatically? No. Failover is a manual action in this version.
 8. What if the Agent crashes mid-sync? The running command’s lease expires and it becomes FAILED_AGENT_LOST; a new
    command must be issued.
 9. What if several companies are open in Tally? The Agent names its company in every request and confirms the result by
    GUID.
10. What stops an Agent from being moved to another company? The GUID check on every sync; a mismatch halts the Agent
    and requires re-registration.
11. Can the Agent keep Tally running? No. Tally must run in a logged-in Windows session; the Agent reports when it cannot
    reach Tally.

Tally, TDL and XML

12. Why custom TDL instead of Tally’s default reports? To control exactly which fields are returned and keep the format
    stable.
13. What if the TDL isn’t loaded? The Agent reports TDL_NOT_LOADED and does not fall back to default reports.
14. How do you know Tally behaves as assumed? A 29-item validation gate must pass on a live installation before dependent
    features are declared complete.
15. Why limit the Tally request size? Very large exports can stall Tally; requests default to 5,000 vouchers, maximum 10,000.
16. How do you verify the XML contract? Fixed XML fixtures are parsed in CI and compared with expected database rows.

Database and identity

17. Why not use voucher number as the key? Numbers repeat across financial years and can be edited; Tally’s GUID is stable.
18. How is a journal with several debits and credits stored? As several voucher_entries rows under one voucher header.
19. Why is there company_id everywhere? So more companies can be added without changing the schema, and so every
    query can be scoped to one company.
20. Why no closing balance column? A balance depends on the date. Opening balances are stored and balances computed,
    then checked against Tally.

Synchronization

21. How do you detect a modified voucher? Its ALTERID is higher than the stored value.
22. Why are watermarks per collection? Collections change independently; one shared counter could skip changes.
23. What if an older record arrives after a newer one? It is rejected as stale; the newer data is kept.
24. Why both a lease and stale protection? The lease stops two Agents writing at once; stale protection stops out-of-order data
    from any writer.
25. How do you update a modified voucher’s lines without a line ID? Its lines are deleted and re-inserted in one transaction.
26. How are deletions detected? A key-only list after each incremental sync, with the daily reconciliation as a backstop.
27. What happens to a cancelled or deleted voucher? It is kept with status CANCELLED or MISSING_IN_TALLY and excluded
    from standard analytics.
28. How does a failed sync recover? Committed batches stay, the watermark marks progress, and the next run resumes
    without duplicates.

Accounting correctness

29. Why not sum every entry of a Sales voucher? Debits and credits cancel out; only credits on sales ledgers count.
30. What exactly counts as a sale? Credits on ledgers whose primary group is Sales Accounts, on active vouchers whose base
    type is Sales, minus linked returns, excluding tax.
31. Why use primary groups? Groups are nested; checking only the immediate parent would miss sub-groups.
32. What about custom voucher types? Each is resolved to its base type, so a Sales-derived type counts as sales.
33. Is every Credit Note a sales return? No. Only one linked to an original sales bill; others are shown separately.
34. Why can’t product revenue equal total sales? Invoices can include non-stock lines, and product-line amounts may be
    computed on a different basis; the gap is shown as Product Attribution Difference until proven.
35. Why don’t the Top 10 customers add up to total sales? Top-N is a subset. The full customer list plus unattributed revenue
    does.
36. What happens to a cash sale? It is Unattributed Customer Revenue, never assigned to an invented customer.
37. Why are Contra vouchers excluded from cash flow? They move money between the company’s own accounts.
38. Are journal entries in cash flow? Excluded by default; a company can enable them.
39. Is GST analysed? Not in v1 by default; revenue is at taxable value. Bringing GST in scope is a business decision.

Reconciliation, aging and stock

40. How do you prove the database matches Tally? Totals from a separate TDL Totals Collection are compared with local
    figures under stated tolerances.
41. When does reconciliation pass? When either the absolute or the percentage difference is within tolerance; it fails only
    when both are exceeded.
42. What if Tally’s value is zero? It passes only if the local value is also zero.
43. How is aging computed? Per bill reference from due dates, with separate “Not yet due” and “Due date unavailable”
    categories.
44. How do Advance and On Account affect aging? They are not in buckets; they appear as separate lines, per customer or
    supplier side.
45. What is Never Sold stock? Stock above zero with no sale in the entire synced history.
46. How do you know current stock without syncing delivery notes? From Tally’s own closing-quantity snapshot on each sync
    date.

Security, AI and operations

47. How is data isolated between companies? Every query is filtered by the company from the authenticated session, enforced
    on the server.
48. How is the Agent authenticated without HMAC? A per-Agent bearer credential over TLS, stored hashed and rotatable.
49. Could Claude report a wrong number? No. All numbers are computed first; Claude only explains them.
50. Does the system work without Claude? Yes. Anomalies are still detected and shown; only the explanation is missing.
51. What data does Claude see? Only the stored evidence for one anomaly.
52. Can a fresh sync restore everything? Only records still in Tally; deleted history needs a database backup.
53. What are the performance targets based on? A recorded benchmark environment and a fixed dataset, not a general
    guarantee.
54. Did you copy an existing product? Two existing tools were used as references. Reconciliation, lifecycle handling, stale
    protection, RBAC, multi-Agent coordination and the validation gate are not in either.
